# Short Reflection Report

The main challenge in refactoring the e-commerce schema was balancing fast operational queries with the new need for large-scale analytics. The original design stores customer and item snapshots inside each order, which makes order retrieval straightforward and preserves purchase-time details. However, repeatedly scanning operational orders for sales trends could increase database load and slow checkout as usage grows.

The new requirements changed my design decisions. I retained orders as the authoritative source for current order status and added an append-only `order_events` collection to record business events. A separate `product_sales_daily` collection stores pre-aggregated metrics, allowing dashboards to query summaries instead of processing every order. I also proposed sharding for collections with high traffic and replication across failure domains to improve fault tolerance. A `customer_order_lookup` collection can support targeted order-history queries when the primary orders collection is sharded by order ID.

These changes improve scalability by distributing data and workload across shards, and improve availability through replica-set failover. Indexes aligned to common query patterns support faster product browsing and order retrieval, while pre-aggregated metrics improve analytics query performance. The design introduces trade-offs: event processing and aggregates may be temporarily stale, duplicated data must be reconciled, and shard-key choice affects query efficiency. During a network partition, strong consistency and unrestricted availability cannot both be guaranteed for every partition. I would validate the design with workload-based load tests, failure simulations, monitoring, and reconciliation checks before production deployment.
